# 実例: t-wada氏のClaude Code × Red/Green TDDでの人間主導の設計議論

出典: [t-wada氏「素のClaude CodeとTDDで初見のお題に挑む」（2026-10-28）](https://t-wada.hatenablog.jp/entry/red-green-tdd-with-claude-code-202610)

これは**公開記事の設計判断を独自の言葉で整理した学習用ケーススタディ**。元記事の全文転載・セッションログの複製ではない。判断の正確な文脈や詳細なプロンプトはリンク先を参照する。

## この事例の使い方（必須）

**題材をモルックに固定するのではなく、設計の順序と人間・AIの役割を再現する。** コードを書く前に、**現時点で公開/確認済みの仕様に必要な決定すべて**を、実際のリポジトリに即して人間と確定する。未知の将来仕様は推測して設計しない。次の仕様が来たら、同じ設計ゲートに戻る。

- **AI:** 既存実装と要件を調べ、まず人間に「ユーザー入力→既存関数の呼び出し→新規処理→応答」の粗いリレーを考えさせる質問をする。人間が困ったら、確認できたコードを使い1〜2文のヒントを出す。
- **人間:** リレーを自分の言葉で説明し、まずどの範囲まで作るか・どこを議論したいかを考える。困ったらAI案を叩き台にする。
- **AI:** 当該仕様に必要な未決定事項を見つけ、具体的な入出力例と比較案を**1つずつ**出す。必要な論点を人間が自発的に見つけられなくても補う。
- **人間:** 代替案との違いと採用理由を理解し、各設計判断を選択・修正・承認する。
- **AI:** 決定を仕様/テストへ反映し、テストリストと実装計画を示す。**両方の承認まで本実装・TDDに入らない。**
- **実装時:** 新たな重要な論点が判明したら、実装を中断して設計を再承認する。

## 具体例: 記事の各段階で実装前に決めたこと

### 事前準備（13:12）

**人間の方針:** TypeScriptで進め、Red/Green TDDを行う。ツールとコミット運用の前提を決める。

**AIの作業:** 実行環境・検証コマンド・開発基盤を整え、指定されたルールを記録する。

**Skillへの一般化:** 言語やフレームワークを自動で新規採用させない。既存環境を優先し、必要な検証方法と変更単位を実装計画前に確認する。

### STEP 01-1: 1本のスキットルから点数を求める（13:32）

**人間の最初の設計仮説:** 今の仕様だけを対象に、小さい関数型のモデルで進める。番号も点数も同じ `number` にすると意味が混ざるのではないか。

**人間とAIが設計合意した項目:**
1. **対象範囲:** 今回は「1本の点数」だけ。先の複数本・投てき記録のための構造は作り込まない。
2. **データの意味・型:** `SkittleNumber` は1〜12のリテラルユニオン、`Skittle` は番号を保持する読み取り専用オブジェクト。点数 `Points` は計算可能な数値の別名。
3. **責務・関数:** スキットル生成と、番号から点数を求める純粋関数 `pointsOf` を分離する。
4. **不正な入力の扱い:** 0・13・小数など、型で排除できる範囲外番号は型検査に委ねる。当該段階では実行時の入力検証は追加しない。
5. **代替案の却下理由:** 番号を単なる数値リテラル型にすると、点数と混同する余地が残る。すべてをブランド型にするのは現時点では過剰。
6. **テストの意図:** 代表的な番号の点数、型レベルで不正番号を拒否すること、番号と点数の混同を防ぐことを守る。
7. **実装計画:** 関数と型の置き場所、テストファイル、型検査方法、Red→Greenの順番を実装前に合意する。

**Skillの質問例:** 「番号と点数は数値だけど同じ型で十分？ 間違って渡されたら何が起きる？ まずどこまでの型/関数を作る？」

### STEP 01-2: 0本・2本以上と、同一番号の重複（14:07）

**新しい仕様で見直した項目:**
1. **関数の入力契約:** 複数本に対応する可変長引数。前STEPの呼び出しを保ちつつ0本も表せる。配列渡し・`Throw`型の新設と比較し、後者はまだ導入しない。
2. **公開動作:** 0本は0点、1本は番号、2本以上は本数。
3. **不変条件:** 同じ投てきで同じ番号のスキットルを二重指定しない。
4. **静的/動的な保証:** 重複を型で防ぐ案を調べたが扱いに問題があるため、実行時に重複を検出する。
5. **エラー方針:** 重複を無視して集合扱いにするAI案ではなく、不正な状態を明示的なエラーで知らせる案を人間が選択した。
6. **設計原則の変更:** 可能なら静的に、難しければ実行時に検証する方針にADRを更新した。
7. **テストと実装順:** 2本、0本、3本、隣り合う/離れた重複など。どの順ならテストが実際に失敗するかを計画で検討した。

**Skillの質問例:** 「同じ番号が2回渡されたら、1本として数える？ エラーにする？ その違いは誰に影響する？」

### STEP 02: 投てき履歴から現在得点を求める（14:50）

**人間とAIが合意した項目:**
1. **入力とモデル:** 単なる点数列ではなく**投てき列**を受け取る。投てきは今の仕様では読み取り専用スキットル配列の別名で十分。毎回 `pointsOf` を再利用する。
2. **計算方式:** 保存された「前回の得点」に加算して更新する方式と比較し、**全投てきの履歴から毎回合計**する方式を採用。現時点で状態の管理を増やさない。
3. **公開契約:** `scoreOf` の入力、返す得点、投てき0回・0本投てきなどの意味を決める。
4. **未定義の仕様:** 別投てきで同じ番号が出ることは許す。得点上限を追加しない。途中の投てきが不正ならそのエラーを伝え、部分得点を返さない。
5. **テストリスト再検討:** 人間が不足を疑ってAIに追加調査させた。0回と0本の違い、途中の空投てき、同じ番号の別投てき、上限なし、途中エラー、型混同などを追加。
6. **設計/テスト/実装計画の承認:** 決めた入力と出力、境界・異常・型の確認を、どの順でTDDに使うか実装前に整理した。

**Skillの質問例:** 「得点は毎回履歴から計算する？ 前回の得点を更新する？ 何を正本として残す？」

### STEP 03: 得点の推移を返す（16:24）

**人間が問題提起:** 履歴配列の要素は、各回の獲得点数か、その時点の累積得点か。

**AIの作業:** 具体例（累積 `[5,16,16,19]` と各回 `[5,11,0,3]`）について、どちらの解釈が仕様文・例・用語に合うかを両面から比較した。

**人間の決定:** 「得点の推移」は累積得点の配列と解釈する。`scoreHistoryOf` の入力と出力をその契約で設計し、テストへ落とす。

**Skillの質問例:** 「APIの『履歴』はイベント列？ その時点の状態のスナップショット列？ 具体例で戻り値を1つ書くと？」

### 品質保証・運用の判断（16:01／17:03、各段階で必要になったら設計へ戻す）

- カバレッジ、Mutation Testing、CIをどう導入・検証するか判断。
- 型チェックだけに任せる箇所に実行時の**表明（assertion）**を加えることを判断。ユーザー入力を拒否する**検証（validation）**とは目的が異なる。
- 表明がMutation Testingの評価と衝突する問題に対し、基準・除外の扱いを議論し、ADRに残す。
- Property-based Testingの適用を検討して導入。
- 環境準備・各仕様の変更をPRでどう切り分けるか判断。混ざったPRを後から積み直す場面もあった。

**一般化:** すべての機能に全ツールを機械的に強制しない。今回の変更に関連する品質条件・検証方法・PR分割を、実装前の計画に含める。後で新しい技術的リスクが分かったら、その部分の設計ゲートを再開する。

## 対象機能の「設計で決め切る」ための短い決定台帳

AIはユーザーに一覧を一度に投げない。**内部では全部点検し、必要な1項目ずつ質問**する。設計承認前、対象となる行は必ず **決定済み／対象外（理由あり）／意図して保留（実装前に影響しない根拠あり）** のいずれかにする。実装動作に影響する未解決事項を保留のまま通してはいけない。

| 事項 | 決める具体的なこと |
| --- | --- |
| 仕様の範囲 | この段階で作るもの、将来へ回すもの、変えない既存動作 |
| ユーザーとの契約 | 入力・期待レスポンス・画面変化、0件などの空ケース |
| 処理のリレー | 既存の関数をどこで呼び、新規関数をどこへ足し、何を受け渡すか |
| ドメイン表現 | 値の意味、型、禁止したい混同、不変条件 |
| 関数・責務 | 主要関数の入力と戻り値、ロジックの持ち主、再利用する処理 |
| 状態・計算 | 正本、保存場所/寿命、導出か更新か、変更できる主体、並行処理 |
| 入力と失敗 | 不正値・重複・境界・権限・外部障害・部分成功・戻り値/エラー |
| 設計の選択 | 有力な代替案、選ぶ理由、見送る理由、撤回する条件 |
| テスト | 守る正常・異常・境界・型・回帰、具体例、実装順 |
| 計画・検証 | 変更ファイル/関数、最小のTDDサイクル、必要なCI/品質確認、PR分割 |

### ゲート運用の注意

- **設計ゲートA:** 上の決定が今回の仕様について完了し、本人が設計を承認したら、テスト/実装計画に進む。
- **計画ゲートB:** テストケースの期待値とTDD順序、実際に変更するファイル/関数を人間が承認したら、初めて実装に進む。
- 「全部設計する」は**現在確定している仕様の中で**という意味。この記事自体もSTEPが増えるごとに設計を更新している。
- このケースの`number`や`Throw`、Mutation Testingの選択を別プロジェクトにコピーしない。**参考にするのは議論の方法と判断基準**。
