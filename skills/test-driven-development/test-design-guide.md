対象機能・変更：
〈ここに実装したい内容を書く〉

仕様・守りたい意図：
〈仕様、受け入れ基準、変更後も維持したい振る舞いを書く。未記入なら関連資料から確認する〉

今回はテスト設計のみを行う。コードやファイルは変更しない。

## 変更範囲と、維持すべき振る舞い

テスト設計の前に、対象操作について次の3点を明記する。

1. 変更してよい振る舞い・データ
2. 変更後も維持する振る舞い・データ
3. 影響を受け得る既存機能と、その接点

影響を受け得る機能は、呼び出し関係、共通処理、共有データ、イベント・外部送信から特定する。根拠なく全機能を対象にしない。

各接点について、既存テストが「維持すべき振る舞い」を確認しているか調べる。不足している場合だけ、範囲外への影響を検出する回帰ケースを採用する。

状態を更新する操作では、更新結果に加え、同じ操作で誤って更新され得る対象外の値が維持されることを確認する。比較対象は仕様上維持すべき項目に限定し、更新日時など変更が許される項目まで固定しない。

各ケースに「守る既存機能・データ」と「検出する巻き込み変更」を記載する。正常系ケースで同時に確認できる場合は統合する。

ファイルの編集範囲は動作テストと分ける。実装時には、合意した変更可能ファイルとGit差分を照合し、範囲外の編集があれば、テストの成否に関係なく報告する。

## 1. 目的と根拠

テストの目的は次の2つとする。

- 今回の実装が要求された振る舞いを満たすことを確認する。
- 他の開発者が将来変更したとき、維持すべき振る舞いが壊れたら検出する。

最初に、リポジトリの指示、対象の仕様、呼び出し元、関連実装、既存テストを確認する。

期待結果の根拠は「今回明示された要求 → 承認済み仕様 → 既存の公開契約」の順に採用する。既存コードの挙動だけを理由に、バグかもしれない挙動を正解として固定しない。

仕様は「整合性・網羅性・明確性・実現性・テスト可能性」で確認する。期待結果が決まらない箇所は「要仕様確認」とし、具体的な論点を示す。仕様や数値、エラーメッセージを推測で確定しない。確定している部分の設計は先に進める。

## 2. 固定するもの

各テストに「将来も守る振る舞い」と「どんな誤変更で失敗するか」を1文ずつ書く。

固定する対象は、公開された入力に対する戻り値、例外、状態変化、画面表示、保存結果などの契約とする。

内部関数の分割、ローカル変数、処理順序、使用ライブラリなど、仕様に影響しない実装詳細は固定しない。内部実装を変更しても、公開契約が同じならテストは通る設計にする。

例：

- 守る振る舞い：チャットルームのメンバーはメッセージを投稿できる。
- 検出する誤変更：権限判定の変更によって、一般メンバーまで投稿を拒否される。

## 3. 関数名

対象関数と、新しく必要になるテスト用関数の名前は、簡単な英単語と自然な語順で付ける。

- 操作は「動詞＋対象」を基本とする。例：\`createMessage\`、\`getChatRoom\`。
- 真偽値を返す判定は\`is\`、\`has\`、\`can\`から始める。例：\`isMember\`、\`canPostMessage\`。
- 意味を説明できない略語や、役割が分からない\`handle\`、\`process\`だけの名前は使わない。
- 短さより理解しやすさを優先する。条件が必要なら\`ByUserId\`などを加える。
- 既存のドメイン用語と公開関数名を優先し、今回の設計だけのために改名や新しい関数分割を行わない。
- テスト名は「条件 → 期待する結果」を日本語で記述する。英語の識別子が必要な場合は、同じ意味を簡単な英語で表す。

## 4. 作らないテスト

次のテストは採用しない。

- 削除済みの関数・ファイル・プロパティが存在しないことだけを確認する。
- ソースコードに特定の文字列や実装が含まれないことだけを確認する。
- TDDの対象関数が未実装であることを期待結果にする。
- 仕様にない機能、将来の拡張、実際には到達できない状態を仮定する。
- 既存テストと同じ入力区分・期待結果・退行を重複して確認する。
- モックが設定どおりの値を返すことや、実装をそのまま書き写した計算だけを確認する。

ただし、「未登録IDを渡したら定義済みのエラーになる」など、入力に対する業務上の振る舞いは異常系の候補に含める。

TDDでは、対象が未実装でも、仕様を満たしたときの結果を期待するテストを設計する。

## 5. ケースの選び方

## テスト候補の洗い出し

代表ケースを選ぶ前に、今回の要求と変更範囲について、以下の観点を確認する。

1. 入力：未入力、空文字、null、不正形式、重複、最小値・最大値。
2. 権限：未認証、権限不足、別ユーザー・別所属のデータへのアクセス。
3. 状態：操作前後の状態、許可される遷移、禁止される遷移、同じ操作の再実行。
4. 競合：連打、二重送信、同時更新、処理順序の逆転。
5. 外部依存：通信失敗、タイムアウト、外部API失敗、再試行。
6. 整合性：部分成功、途中失敗、ロールバック、保存結果と返り値の一致。
7. 回帰：呼び出し元、既存の公開契約、今回変更しない機能への影響。
8. 非機能：仕様に定義された性能条件、機密情報の扱い、環境・日時の差。

各観点は次の規則で扱う。

- 対象機能に関係しないものは、理由を付けて対象外にする。
- 関係するが期待結果が未定義なら「要仕様確認」にする。AIが仕様を追加しない。
- 現実に発生可能で、要求に根拠があるものだけをテスト候補にする。
- 関数・ファイルなどの不存在だけを確認するケースは作らない。
- 複数条件が結果を変える場合は条件と結果の対応表、状態が変わる場合は遷移前・操作・遷移後の表で整理する。表の全行を自動的にテストへ採用しない。

候補ごとに「守る要求」「具体的な入力・状態」「期待結果」「失敗時のユーザー影響」「既存テストで検出できるか」を整理する。

その後、「ケースの選び方」に従って正常系・異常系・境界の代表ケースを選ぶ。洗い出した候補をすべてテストにする必要はない。

ただし、選ばなかった候補のうち、権限逸脱・情報漏洩・データ破損・主要機能停止につながるものは、既存テストで検出できなければ「重要な追加候補」として必ず示す。発生頻度が低いことだけを理由に省略しない。

最終出力の「追加候補・除外・要仕様確認」には、この洗い出しで残った項目と理由を記載する。

今回変更する独立した公開の振る舞いごとに、次の順で選ぶ。全関数を機械的にテスト対象にしない。

### 正常系：最も難しい代表ケース

「難しい」は、仕様上成立する1回の操作で、最も多くの業務条件・状態変化を確認できることと定義する。

候補が複数なら、次の順で選ぶ。

1. 確認できる業務条件が多い。
2. 確認できる状態変化が多い。
3. 壊れたときのユーザー影響が大きい。
4. 仕様の記載順が先である。

入力を無意味に巨大にしたり、登録・編集・削除など別の操作を1件に詰め込んだりしない。1ケースは1つの主要な振る舞いを確認する。関連する複数の結果は同時に検証してよい。

### 異常系：最も起きやすい代表ケースを

発生実績があれば、発生頻度が最も高いものを選ぶ。実績がなければ、次の順で選び、「発生頻度は未計測」と明記する。

1. 仕様や運用記録で頻出とされる失敗
2. 通常操作で起きる単独の入力ミス
3. 通常利用する外部サービスの単独の失敗
4. 複数の特殊条件が重なって起きる失敗

同順位なら、ユーザー影響が大きいもの、次に仕様の記載順で選ぶ。

1ケースで不正にする条件は1つとし、それ以外は正常にする。対象に異常系の契約がなければ0件とし、理由を書く。

### 境界：判定が切り替わる最小の値を選ぶ

- 真偽の2値だけを持つ独立した条件は、trueになる入力とfalseになる入力の2件。
- 単一の閾値で判定が切り替わる場合は、境界に最も近い両側の2件。整数の\`x >= 18\`なら\`17 → false\`、\`18 → true\`。
- 上下限がある場合は、それぞれの境界を確認する。整数の\`1 <= x <= 100\`なら\`0・1・100・101\`。
- その他の境界は、仕様上の最小単位で「直前・境界・直後」を候補にし、同じ判定を重複する値を除く。日付・時刻は単位とタイムゾーンも固定する。
- 戻り値がbooleanでも、独立した条件や境界が複数ある場合は、全体を2件だけに省略しない。
- 境界がない対象には境界テストを作らない。

正常系・異常系と同じ前提、入力、期待結果になる境界ケースは、1件に統合して複数の分類を付ける。

### 追加ケース

上記と既存テストで守れない独立した要求がある場合は、「追加候補」に分ける。

各候補には、未検証の要求と、既存の採用ケースでは検出できない誤変更を書く。権限逸脱・データ破損・主要動線停止につながる候補を先に示す。ケース数を増やすだけの網羅は行わない。

## 6. テストする層

その誤りを検出できる最小の層を選ぶ。

1. 純粋な業務判定・計算・状態遷移：単体テスト
2. DB制約やAPIなど、接続部分でしか検出できないもの：結合テスト
3. 画面操作からの接続でしか検出できないもの：UI/E2Eテスト

単体テストで検出できるものをE2Eへ重複させない。domainのテストにDB・HTTP・モックを持ち込まない。UIのテスト方式と配置はリポジトリの既存ルールに従う。

時刻・乱数・外部応答は必要に応じて固定し、実行順序や固定時間のsleepに依存しない。LLMの自由回答など、毎回変わる出力の品質評価は別枠にし、完全一致の単体テストを作らない。

## 7. 出力

以下の4項目だけを、簡潔に出力する。

### A. 守る仕様と対象関数

仕様ごとに\`R1\`からIDを付け、次を記載する。

- 根拠
- 維持する振る舞い
- 対象関数名と役割
- 既存テストで確認済みの範囲

### B. 採用するテストケース

各ケースに次を記載する。

- ID・種別・テスト名
- 対象関数・テストする層
- Arrange：具体的なデータ・状態
- Act：具体的な引数と1つの主要操作
- Assert：具体的な戻り値・例外・状態
- 対応する仕様ID
- 検出する誤変更
- このケースを代表として選んだ理由

「正常に動く」「エラーになる」だけではなく、何がどうなるかを記載する。まだ実行していないため、結果をPASSと書かない。

### C. 追加候補・除外・要仕様確認

採用外の重要な観点と、その理由を記載する。未検証の要求を「確認済み」にしない。

### D. TDDの実装順

採用ケースのIDを、公開契約の基本動作 → 例外 → 境界・追加条件の依存順に並べる。独立したケースは影響が大きい順、同順位はID順とする。

ケースの一覧は先に設計するが、実装時には1件ずつ「失敗するテスト → 意図した理由で失敗を確認 → 最小実装 → 成功確認 → 必要な整理」と進める。

出力前に、各ケースについて「このテストを削ると、どの誤変更を検出できなくなるか」を確認する。答えが他の採用ケースと同じなら統合し、答えがなければ除外する。
