# QAプロンプトの設計方針と参照観点

対象：[実装後QA・回帰確認プロンプト](../prompts/qa-review.md)

QA運用方針、既存のQA指示、API・DB・テスト設計に関する提供資料を参考に、個別プロジェクトで再利用できる確認項目へ整理した。元資料の本文、社内リンク、個人PCの保存先は掲載しない。この説明をQA実行時に毎回AIへ渡す必要はない。

## 6つの設計方針

| 方針 | プロンプトへの反映 |
|---|---|
| 1. 用途を固定する | 冒頭・1節。実装後のQA、ケース設計、既存テスト・実API・UIでの検証。TDD実装や修正とは分離する。 |
| 2. 差分の選び方を統一する | 2.2節。比較元と対象版を記録し、ブランチ・ステージ済み・未ステージ・未追跡の最終状態を評価。対象なしで全機能QAへ広げない。 |
| 3. リリース判定を重複させない | 6節。NO-GO → BLOCKED → CONDITIONAL GO → GOの順で1つを選ぶ。未確認、Minorの受容、改善提案を区別する。 |
| 4. 観点の充足と全ケース実行を分ける | 3・4・7節。適用理由を判断し、要求→ケース→証拠を対応付ける。全項目の機械的なケース化を避ける。 |
| 5. 検証方法を具体化する | 3・5節。最小の有効なテスト層、実API・UI、決定的／非決定的評価、実行結果と未実行の区別を明示する。 |
| 6. 合意範囲と対象環境を固定する | 2.3・5節。変更範囲の逸脱と動作の巻き込みを分け、未変更の利用元も追跡する。検証環境が対象版であることを確認する。 |

追加で、4D・4Eにセキュリティと性能の具体的な確認を置く。単純な命名、業務意図の回帰保護、代表的な正常系・異常系・境界ケースを3節に定義する。未要求の機能の不存在だけを検証するテストは除外するが、拒否・副作用の抑制・テナント分離は除外しない。

## QA運用資料から採用した原則

- テスト件数や成功表示ではなく、要求された振る舞いの証拠を残す。
- 事業への影響で重点化し、実装と独立した期待値を用いる。
- 仕様正本、派生したテスト設計、実装の現状を混同しない。
- 実ブラウザでの探索、検証対象版の確認、専用データの利用を行う。
- 決定的な機能と非決定的な出力で評価方法を分ける。
- 手動で確認した重要な契約は自動回帰テスト候補として残す。自動化未実施だけで不合格にはせず、必須条件と未確認リスクで判断する。

動画画面のOCR資料からは、値の選択肢と過去参照、論理削除と既定の絞り込み、ドメインモデル、業務理解、リソースとイベント、マルチテナントとRLS、パーティションと複製の7つの題材を確認した。

このDOCXは音声の逐語録ではなく画面OCRで、文字化け・重複・広告表示が多い。判読できない図やコードを推測で復元せず、読み取れた原則だけを採用した。元動画の再視聴・再OCRは行っていない。

## 意図的に必須化しなかったもの

- 機能範囲、履歴・集計構造、削除方式等が異なる設計案を混ぜて一つの正解にしない。対象プロジェクトで承認された設計を使う。
- 資料の日付が新しいだけで採用済みとしない。仕様・承認記録との整合を確認する。
- 特定のテーブル数、主キー型、外部キー・ENUM・論理削除の禁止、gRPC・REST・CQRS・RLSの採用、固定のタイムアウト・件数・鮮度、インフラ構成は一般的な合格条件にしない。
- インデックスや集計構造の採用だけで高速・整合的とみなさず、競合、実行計画、代表データによる実測で確かめる。古い資料の製品機能・性能値を現行環境へ当てはめない。
- 組織構造、業界動向、エディタ設定、サンプル資料の確認を毎回の合否条件にしない。多数の分類ラベルのために原因・混入工程を推測しない。

## 限界

提供された資料とQA運用資料から必要な観点を統合したものであり、リンク先の全資料を再帰取得したものではない。あらゆる不具合・攻撃・性能問題の不存在を保証するものでもない。プロンプトは適用範囲と未確認事項の明示を必須とする。
